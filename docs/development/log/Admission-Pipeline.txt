AO Nexus: acceptance-controlled Rebirth login
===========================================

Evidence
--------
Inspected upstream server revision 2d4edfded3bfee27f5c89753e1250e9c94b107e7
in the separate server-source checkout. WorldState was inspected with
git show HEAD, so this conclusion does not rely on the local pending-grants
patch in that separate repository. No server files or deployment were changed.

In WorldEngine/State/WorldState.cs, BeginLogin replaces the account's pending
generation. Claim rejects a login ticket whose generation is no longer current.
Successful Claim creates/refreshes an independent character lease and removes
the ticket. Starting the next authentication after Claim avoids that race.

ZoneEngine_New/Core/MessageHandlers/ZoneLoginHandler.cs awaits ClaimAsync at
line 116, closes rejected sessions at 123-131, and only after successful admission
and hydration sends InitiateCompression, ChatServerInfo, then PlayfieldAnarchyF
at 216-218. ChatServerInfo is therefore evidence of completed admission on this
path. It is not a promise that later rendering, spawn or networking cannot fail.
The exact revision deployed on the public endpoint has not been independently
verified. Live tests corroborated the observed response and successful sequencing.

Client implementation
---------------------
The version-pinned MessageProtocol.dll DataBlockToMessage export exposes decoded
frames after decompression. The hook calls the original decoder first, then
recognizes a successful SystemMessage 0x43 addressed to the requested character.
It checks the complete frame length and only reports once after character
selection. It neither logs packet payloads nor changes the game protocol.

Each preloaded client waits on private local ready/cancel events before its
normal ConnectToLH call. A UI-thread timer checks readiness; the UI thread is
never blocked waiting for the previous client. Readiness is released on receipt
of ChatServerInfo. Cancellation, launcher exit, missing gate handles and gate
timeout leave the manual login UI available without authenticating automatically.
There is no configured delay between successive authentications. A timer dispatch
and normal scheduling latency remain; the timer is not a server-readiness guess.

The queue retains final character-window confirmation, session identity checks,
account limits and normal /quit. Missing acceptance telemetry falls back to full
confirmation. Failed confirmation stops further starts in that account queue.
Already-preloaded clients whose prerequisite fails are cancelled, not force-killed.

Scope and controls
------------------
Enabled by default only for 2.24.96.30:7500 with FastStartup enabled and all six
classic-client hashes verified. Unknown builds, Funcom and PRK retain serial
behavior. Turning off Fast loading also disables preloading. Internal stdin
request controls AcceptancePipeline=false and MaxConcurrentPreloads=1..6 allow
bounded local comparison. Unsafe fixed-delay experiment controls were removed.
No UI setting or saved profile was rewritten by the experiments.

Visible loading timers
----------------------
Each newly confirmed client now gets a readable activity-log line, for example
"Character loaded in 9.56 s." The interval starts immediately before client spawn
and ends at its native world-ready report. It includes preload/admission waits.
The final team time runs from launch-queue entry to the last new client's
world-ready event. It includes gaps between starts; it does not add overlapping
per-client times or include initial launcher-component preparation.

Existing clients are excluded from new-client loading time. An entirely reused
preset reports that no clients needed loading. Missing world-ready reports use
explicitly labelled login-confirmation times instead. Partial/failed runs report
elapsed run time and the confirmed/selected counts rather than claiming that
all clients loaded. English and Danish text and number formats are supported.

The timing-log verification run confirmed all six individual displayed values
against native events. The visible team total was 9.92 s; the external helper's
last world-ready timestamp was 10.088 s, including earlier request preparation.
This subsequent warm run had different timing from the earlier benchmark;
the logging change does not itself establish a performance improvement.
Reuse and normal logout also passed. See logs/aor-visible-timing*.txt.
112 policy/admission/timing checks and 51 creation-monitor checks passed; the
200-file payload was verified. A synthetic UI render checked the left-aligned
credit and delivery of timing messages into the visible activity log.
